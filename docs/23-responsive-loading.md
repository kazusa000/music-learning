# 启动、工程加载与讨论响应

2026-10-19。用户将复杂音乐核对闭环后置，优先要求 AI 接入容易使用、打开工程快、讨论不卡顿。本次不增加音乐审核流程，不运行三模型或新的 Codex 推理。

## AI 接入现状

真实 Codex 整曲/局部讨论、引用、自然语言改编及渲染已有 P4/P5/P6 证据。应用保存讨论和工程，供应商 thread 仍为临时会话；打开网页不会启动 Codex 推理。默认仍是应用独立登录；用户主动选择既有登录后，网页只记住登录模式，不保存或复制凭据。模型仍依据事件和存储测量，没有直接音乐音频输入。

## 本次变更

- 启动器不再为了启动/状态检查提前导入 FastAPI 和数据库迁移模块；会话 helper 独立为 session.py，实际服务及监督进程仍按原边界管理。
- 页面连接只检查轻量 health，不再先获取全部操作 schema；AI/SDK/CLI 的 describe_capabilities 保持完整。
- 页面共用原有一条 SSE，将事件分发到讨论、版本/渲染和试听。首次 UI 连接使用 live_only=true 跳过历史事件；首屏状态仍实际查询，断线重连依 Last-Event-ID 补发并主动刷新各面板。旧客户端不传 live_only 时仍保留原始 cursor/replay 语义。
- 空闲全量刷新由 0.9–3 秒改为事件触发及 15 秒兜底；生成中只每 900 ms 回读活跃轮次，保留停止/重试和部分文本，终态停止该轮轮询。试听指令通过事件即时触发，5 秒轮询兜底。
- 插件详情展开时才获取；讨论工具详情展开时才生成 JSON 内容。记住用户主动选择的登录方式；没有另建默认授权。
- Service 的只读操作使用 SQLite 普通读事务，不占 BEGIN IMMEDIATE 写锁；所有写操作、worker 发布、租约和幂等事务继续使用原来的写事务。

无数据库迁移、无操作数量变化，仍为 51 项操作、11 类任务。describe_capabilities 的 events transport 描述补充 live_only，生成契约无漂移。音乐原始文件、模型输出及正式工程 head 不变。

## 保留的边界

Codex 每轮仍按需启动受限 App Server，供应商网络与生成耗时尚未做新一轮性能测量；没有预热推理或后台自动提问。新版本音频仍需真实 VST3 离线渲染。此次未改工程提交时全依赖摘要校验、快照/投影存储和播放 PCM 缓存；这些性能问题仍需分别设计验证，不能因首屏加快就宣称全部制作路径已优化。

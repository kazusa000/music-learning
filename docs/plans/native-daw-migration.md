## 验收指标与测量方法

以下是首次目标，不是对所有插件／硬件的保证。报告中保留机器、音频设备、采样率、缓冲、工程规模、冷/暖状态及所有样本，至少20次用于中位数/P95；整曲稳定性另测，不以短音伪装长曲验收。

| 指标 | 初始目标 | 起止点／证据 |
| --- | --- | --- |
| 已就绪工程按播放到首声 | P95 ≤150ms | 控制命令时间→设备回环出现有效信号，不用按钮状态代替 |
| 纯音频现成工程冷开到可播放 | P95 ≤1s | 引擎未持有本工程文件缓存→素材首段与设备就绪；操作系统磁盘缓存冷/暖分开记录 |
| 已就绪工程随机定位到新位置声音 | P95 ≤250ms | 定位命令→已知标记的回环信号；不得将旧位置声音计入成功 |
| 音量/静音/独奏响应 | P95 ≤50ms | 控制提交→回环变化，含原生处理提前量；不重新解码或建图 |
| 轻量工程元数据/界面可交互 | P95 ≤1s | 打开动作→轨道可见且交互；插件装载不遮住整个工作台 |
| 原生预读和通信音频缓存 | 默认总预算≤256MiB，独立于插件采样内存 | 引擎/worker缓冲统计；不能通过整曲常驻突破预算达标 |
| 连续播放 | 305s和约396s完整播放＋30分钟循环/操作 | 回环无非预期中断/漂移；underrun/late-block全部记录，标准测试负载0 |
| 同步和样本正确性 | 同采样率合成夹具样本对齐；重采样长期漂移≤1源样本（排除设备固定延迟） | 内核离线捕获与回环对照；硬件延迟单列，不冒充回环本身逐样本精确 |

大型采样音源：报告冷启动、已加载切预设、已有精确冻结音频三种状态；显示实际进度与失败。没有合理证据前不承诺Keyscape/Pianoteq500ms加载，也不把音源内存算进引擎缓存预算来混淆。实时达不到要求时定位原因、明确轨道能力，不能把前端等待转移成设备后台静音。

设备捕获是独立开发验收内容。先用可控小音量夹具和系统回环验证，不修改系统默认音量／默认设备，也不接管用户鼠标。软件探针、真实设备输出、人耳听感分别记录。

## 各阶段回归与保护

- 快照／原版本／幂等／AI整曲默认scope／删除屏障／独奏与手动静音恢复等既有规则不重写成另一套权限系统。
- N1之前抓取**当时**正式九表和head摘要、固定宿主/插件/11保护项摘要及相关进程身份；历史文档里的工程数量不作为当前基线。
- 各阶段使用独立根和端口；读取现成音频需要有清单与SHA，禁止向正式工程造测试修订。音乐模型仅在导入回归有必要时调用，不因设备开发自动重跑。
- 不移动/修改H音源库，不访问NAS，不碰历史拒绝路径，不开第二批或修改Pianoteq固定验证实现。引擎源码新目标和新构建目录隔离，旧库不因编译顺便覆盖。
- 一次用户操作只有一个输出所有者，切换新旧实现先暂停并确认旧输出释放，失败可退回已提交基线。回退不会执行数据库降级或丢弃用户新修订。
- 任务成果分独立Git提交：协议/骨架、文件播放、插件、前端、生命周期、图/导出、验收；每阶段更新此处状态与证据链接。目录移动独立提交，不能把大批路径改名与音频行为一起提交。

按需创建，不预建空模块：`native/engine/{CMakeLists.txt,Main.cpp,DeviceOutput.*,EngineProtocol.*}`；`src/music_learning/engine/{broker.py,compiler.py}`；在既有contracts中添加生成契约；`scripts/build_engine.py`与`scripts/probe_engine_device.py`；`tests/engine/`设备/协议夹具。接口先形成版本化schema再写适配，不复制已有Service业务校验。N2再引入Timeline、FileSource、ReadAhead与Mixer，N3才创建`native/plugin-worker`。

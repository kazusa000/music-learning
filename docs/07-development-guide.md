## 依赖与配置

前端用 pnpm，Python 用 uv，原生宿主用 C++20/CMake。首次安装后提交对应锁文件、CMake presets 与 SDK revision 清单，记录编译器/Windows SDK 版本。服务环境与各模型环境分别锁定，避免依赖解析相互覆盖。

依赖本机已有程序时检查版本和真实功能，不能仅以 PATH 中存在为就绪。FFmpeg 命令可执行不代表 Python 音频绑定兼容；CUDA 设备可见不代表实际模型可运行。

环境样例只包含占位符。AI 密钥、模型访问令牌保存在本地环境或凭据存储，不写入浏览器代码、Git、错误日志、提示词或模型清单。

未来配置至少包含：数据/模型/采样目录、各适配器与原生宿主路径、受控 VST3 扫描目录、GPU 策略、FFmpeg、对话服务标识与能力、可选音频上传设置。模型与插件 manifest 保存版本、摘要、许可、能力、配置和下载来源。

## Git 管理

- 默认分支 `main`；开发功能使用 `feat/<topic>`，修复使用 `fix/<topic>`，文档使用 `docs/<topic>`。小型文档调整可直接在 main 提交。
- 提交包含一个可解释的变化，建议前缀 `docs:`、`feat:`、`fix:`、`test:`、`chore:`。
- 提交前检查 `git diff --check`、暂存文件清单和实际差异；运行与改动相关的检查。
- 不提交用户录音、模型权重、渲染、数据库、个人对话、日志或密钥。测试夹具使用小型自制素材并说明来源。
- 第一阶段不配置远程仓库或推送；远程位置由用户后续指定。本地 Git 只提供本机版本历史。
- 提交者身份使用用户提供的姓名和邮箱；当前缺少配置时先完成文件与初始化，不编造用户身份，也不修改全局 Git 配置。
- 不改写已有用户历史，不以清理工作区为理由删除未提交内容。

Git 管理应用源码；音乐工程使用应用版本系统和独立备份。两者的版本号、撤销和恢复流程互不替代。

## 开发检查

当前提供 ruff、pytest、契约漂移检查、TypeScript 严格检查/构建、Playwright 整曲工作台和真实 SDK 恢复探测；命令见 README、docs/14/15/17。当前原生/模型格式 34 项用 transcription 环境（含 mido），后端 45 项用 app 环境，不能混用缺包的 tooling 环境全量运行。P2/P3 增加冻结的 migrations/0002/0003，不修改旧迁移。

优先测试具有明确失败风险的逻辑：全操作接口、插件扫描/崩溃、参数/状态/预设、路由/延迟/自动化、时间映射、任务恢复、编辑范围、原子发布、幂等、版本冲突和数据迁移。视觉文案等低影响调整以适当界面检查为主，不编写只重复实现的测试。

小型夹具验证确定性逻辑，真实 VST3、模型与完整录音验证能力。核心工程流程通过 API/SDK/CLI 完成，不能用录制鼠标操作冒充自动化接口。真实对话接入、结果试听和人工听辨的缺口不能由 mock 替代。

## 运行与退出

正式交付提供 `start.cmd`、CLI、诊断和停止入口。启动器检查依赖、数据库迁移、端口、原生宿主、模型/插件/采样和配置。Agent 可只启动服务与 worker；需要查看或试听时打开浏览器。后台进程隐藏启动并记录 PID 与归属。

停止时取消或妥善挂起任务、关闭本应用创建的 worker 和子进程、释放端口及 GPU；不终止其他项目进程。长任务的重试/恢复语义见[技术方案](03-architecture.md)。

## 数据迁移与备份

数据库使用有序迁移。迁移前采用 SQLite backup API 或受控停写备份，避免只复制主数据库而漏掉 WAL。恢复在独立目录验证后切换，保存原始备份直到用户确认可用。

工程备份打包 manifest、快照、事务、讨论、插件状态和所需素材。插件二进制/采样库按可移植性与使用条件记录依赖或打包，冻结音频提供缺失资源时的试听。导入校验摘要和相对路径，拒绝越出目标目录的路径。源代码 Git 恢复不能自动恢复被忽略的工程数据。

## 文档维护

产品范围变更更新项目规划；技术选择变更在选型依据记录理由、代价和验证；数据变更同步 schema 与迁移；验收完成后将实际证据写入阶段报告。

每次报告区分：已经实现、已经测量、推断和待验证。任何未完成的目标继续保留，不因代码能启动或测试夹具通过而标记整项完成。
